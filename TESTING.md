# Как самостоятельно проверить агента

Все команды запускаются из корня репозитория, где находятся `agent.py` и
`local_eval.py`.

Полное описание алгоритма, модулей и пути масштабирования находится в
[`PROJECT_GUIDE.md`](PROJECT_GUIDE.md). Этот документ отвечает именно на
вопросы «какую команду запустить» и «что означает её результат».

## 1. Подготовить Python-окружение

Проект использует `numpy` и `pandas`. Создайте отдельное окружение, чтобы не
устанавливать библиотеки в системный Python:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Проверка окружения:

```powershell
.\.venv\Scripts\python.exe -c "import numpy, pandas; print(numpy.__version__, pandas.__version__)"
```

Если команда печатает две версии без ошибки, окружение готово. Активация
виртуального окружения не обязательна: команды ниже можно запускать через
полный путь `.\.venv\Scripts\python.exe`.

Ошибка `ModuleNotFoundError: No module named 'numpy'` означает, что команда была
запущена системным Python вместо подготовленного `.venv` или зависимости ещё
не установлены.

## 2. Получить свежий код

```powershell
git pull --ff-only origin main
git status
```

Перед тестами `git status` не должен показывать неожиданные локальные изменения.

## 3. Запустить автоматические тесты

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Ожидаемый итог:

```text
Ran ... tests
OK
```

Эти тесты проверяют контракт `priors.py`, детерминированность, корректность
тарифов, лимиты бюджета и контактов, работу fallback и наличие разведки
переходов без прямой истории.

Иными словами, `OK` подтверждает техническую корректность текущей версии и
защищает от регрессий. Он не гарантирует прибыль на скрытой выборке: качество
решения проверяется отдельно end-to-end прогонами и устойчивостью на серии
seed.

## 4. Выполнить один полный прогон

```powershell
.\.venv\Scripts\python.exe -X utf8 local_eval.py
```

Проверить в отчёте:

- `Статус: PASS`;
- `ЧИСТЫЙ РЕЗУЛЬТАТ (net)` положительный;
- `Пилотов проведено` больше нуля и не больше 20;
- остаток бюджета и контактов не отрицательный;
- нет сообщений `Кампания ... отброшена`.

Строка `Кампаний: 26` может включать 20 пилотов и 6 финальных кампаний. Лимит
из ТЗ — не более 10 именно финальных кампаний, которые печатает
`make_submission.py`.

## 5. Проверить устойчивость

```powershell
.\.venv\Scripts\python.exe -X utf8 local_eval.py --runs 10
```

Для более серьёзной проверки:

```powershell
.\.venv\Scripts\python.exe -X utf8 local_eval.py --runs 50
```

Смотреть нужно не только на максимум, но прежде всего на:

- число прогонов в плюс;
- минимум;
- медиану;
- изменение знака между seed.

Если часть запусков отрицательная, агент слишком доверяет шумным пилотам.

## 6. Открыть наглядный отчёт

```powershell
.\.venv\Scripts\python.exe -X utf8 visual_report.py
start .agent-report\report.html
```

Отчёт показывает, как один mock-прогон превращает 23 441 доступного абонента в
конкретные пилотные и финальные контакты. Важно различать:

- аудиторию — всех абонентов, из которых можно выбирать;
- контакт — одну доставку одной кампании одному абоненту;
- уникального абонента — человека, которому lift засчитывается только один
  раз, даже если контактов было несколько;
- лимит 15 000 — сумму всех пилотных и финальных контактов, а не требование
  обязательно охватить 15 000 разных людей.

В `.agent-report/` также создаются полные CSV-таблицы контактов, абонентов и
кампаний. Каталог исключён из Git, потому что это результат конкретного
локального запуска. Генератор отчёта не вызывается из `Agent.act(env)` и не
участвует в судейской логике.

## 7. Сравнить priors с fallback

```powershell
.\.venv\Scripts\python.exe -X utf8 benchmark.py --runs 10
```

Команда запускает на одинаковых seed:

1. агента без `priors.py`, только с тарифным fallback;
2. полного агента с историческими priors.

В отчёте сравниваются медиана, 10-й перцентиль, минимум, стоимость, контакты и
число финальных кампаний. Для более устойчивого сравнения используйте:

```powershell
.\.venv\Scripts\python.exe -X utf8 benchmark.py --runs 50
```

Мок-среда построена из той же истории, поэтому преимущество priors локально
ожидаемо завышено. Этот тест доказывает корректность интеграции, но не будущий
результат на скрытой аудитории.

## 8. Пересобрать submission

```powershell
.\.venv\Scripts\python.exe -X utf8 make_submission.py
git diff -- submission.csv
```

`submission.csv` должен содержать от 1 до 10 строк. Повторный запуск без
изменения кода должен создавать тот же файл.

## 9. Финальный чек перед отправкой

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -X utf8 local_eval.py --runs 10
.\.venv\Scripts\python.exe -X utf8 make_submission.py
git status
```

Также убедитесь, что в Git не попали `.env`, ключи, credential-файлы или другие
секреты. Не используйте `__closure__`, `gc`, `inspect` и другие способы доступа
к скрытому состоянию среды. Исторические CSV из официального пакета и
публичный `env.run_pilot()` использовать разрешено.

## Как читать основные метрики

- `gross_arpu_lift` — прирост ARPU до расходов на коммуникацию.
- `total_cost` — стоимость пилотных и финальных контактов.
- `net_arpu_gain` — главный результат: gross минус стоимость.
- `risk_score` — доля охваченных клиентов с отрицательным эффектом.
- `ROI` — gross lift, делённый на расходы.
- `seed` — вариант случайного шума пилотов, а не другая аудитория.

Главный критерий хорошей стратегии — положительный и устойчивый `net_arpu_gain`
на серии seed, а не рекорд в одном удачном запуске.
